# Nokia E7 NCD v0.14.2: guarded child-browse companion elements

**Status:** Built and host-tested. **No E7 v0.14.2 physical test has been performed.** Documentation-only GitHub PR; runnable source/tests ZIP delivered separately in chat. No merge or deployment requested.

## Observed physical evidence, v0.14.1
The E7 received configuration HTTP 200 and first root-browse HTTP 200, then sent a distinct second browse to offline-root. Its sanitized shape: includeMetaData=false; metadataDepth=1; metadataPerLevel=1; pageStart=0; structureDepth=1; pageSize greater than one; one or more additional direct request-root elements. The listener rejected this second browse with HTTP 404; no fictional metadata was sent and the E7 continued spinning. The diagnostic did not reveal exact companion tag names or numerical page size.

## Source-based hypothesis and narrow change
The v0.14 is_child_metadata_request required exactly one root child, browse, rejecting all optional siblings. Historical Nokia source in CNcdRequestBase::CreateRequestL and CNcdRequestConfigurationData permits optional configuration, cookies and queryResponse ahead of browse. The new standalone ncd_guarded_browse_v142.py admits only documented passive siblings in their corresponding Preminet or configuration namespaces, in limited counts, with known nested tag names; it then calls the **unchanged v0.14 child matcher** on an in-memory stripped request to preserve namespace, folder ID, metadata depth, pagination, and child filter guards. A single final browse is required. Unknown/active/extra operations and invalid structures remain HTTP 404. A pageSize above 100 still receives 404, because the handset diagnostic only reported greater_than_one, not the actual number.

### Source-backed candidates to investigate offline before any new live response

The historical `CIAUpdateLoader::OperationComplete` calls the controller's `LoadComplete` only when **all outstanding load operations** have completed (see lines ~323-420): https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdateloader.cpp. The same older loader's `RootExpiredL` explicitly refers to **two CGWs** (Arrow and firmware) and checks root child count against two (lines ~140-180); root folder ref count alone may not establish correct two-gateway topology. Our frozen v0.9 configuration XML declares **one** synthetic content source, whereas v0.14's root browse payload has **two** synthetic top-level FolderRefs (`offline-root` and `offline-secondary`), which are not necessarily equivalent to two separate firmware/software gateways. The NCD loader derives content-source suboperations from each configured content source; see `CNcdLoadRootNodeOperation`, around `EBrowseRequest`: https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadrootnodeoperationimpl.cpp. **These are hypotheses, not demonstrated causes on the Belle handset.** Other possibilities include rejection/ineligibility of the inert, zero-byte application metadata, a different source needed by the UI, or delayed internal state completion.

**Recommended next evidence with no more catalogue requests:** owner can exit the currently spinning Software Update UI normally (no cache reset) and report whether the subsequent screen is a blank directory, an error, or displays the literal fictional item name `E7 Lab Test Update`. This differentiates visible acceptance from a loader/UI stall. Do not rearm v0.14.2 merely to repeat its already proven socket sequence. If deeper investigation is needed, prefer offline parsing against historical Symbian source or passive, bounded network observation. No more mutable-cache trials until there is a specific discriminating hypothesis.

## Post-spinner observation: blank update directory (2026-10-11)

After the **three host-side HTTP 200 socket writes** in the single physical v0.14.2 trial, the handset UI continued spinning indefinitely. On **exiting the checking screen normally**, the owner observed a **blank update directory**, *not* the fictional `E7 Lab Test Update` item and *not* an immediate error message.

**What is established:** the synthetic child response left Sanctuary's socket after a valid Nokia child metadata browse. The phone can display an empty update list after the stalled check. There is **no evidence of visible item acceptance or successful completion callback**; equally the blank list is not proof of private-cache corruption. The observation does not differentiate incomplete loads, invisible/filtered nodes, or parsing failure. The server's `post_child_observation_complete` is only its own timed exit.

**Offline source tracing, with version caveat (these historical sources predate E7 Belle):**

- [`CIAUpdateController::LocalContainerLoadL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatecontrollerimpl.cpp) explicitly **skips uninitialised item nodes**, recursively walks containers, and passes constructed nodes to a node container. This can yield an empty list even if the root operation received data.
- [`CIAUpdateNodeContainer::AddNodeL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatenodecontainer.cpp) refuses candidates failing platform, installation, embedded degradation or package-type acceptance checks; `HeadNodesL` additionally filters hidden/dependency-ineligible nodes. Empty list is therefore **not a parser ACK or NACK**.
- [`CNcdNodeContentInfo::InternalizeL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdnodecontentinfoimpl.cpp) interprets the MIME and package identity for an item's content. Our v0.14 fictional item deliberately advertises `mime=application/octet-stream`, `size=0`, `id=e7-lab-not-a-package` and no package URI. These **non-installable safeguards** plausibly keep it from appearing even if parsed. **Do not replace with a real SIS or package URL merely to force UI visibility.**
- [`CIAUpdateLoader::OperationComplete`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdateloader.cpp) defers `LoadComplete` until the queue of node load operations is exhausted. The loader also expects software and firmware catalogue gateways; current config has one synthetic source, two sibling folders (not established to represent dual gateway topology).

**Next:** focus on offline validation of both the catalogue **completion conditions** and the deliberately inert synthetic item's eligibility against Nokia source. Do not claim that the phone accepted the fictional item or that its cache was fried. No new physical request, cache deletion or binary response is justified solely by this observation. Distinguish an update-list rendering/filtering issue from a stalled completion callback. User has not requested changes to the runnable artifact in this message.

## Offline root-folder initialization audit (2026-10-11, no handset access)

**Concrete fixture mismatch found:** v0.14.2 inherits exactly the same three response bytes from v0.14. A fresh local XML-element-tree count against those exact byte strings and SHA-256 values confirms:

| Stage | FolderRef | ItemRef | FolderData | ItemData |
| --- | ---: | ---: | ---: | ---: |
| Configuration | 0 | 0 | 0 | 0 |
| Root `preminetResponse` | **2** (`offline-root` count=1, `offline-secondary` count=0) | 0 | **0** | 0 |
| Child `preminetResponse` | **1** (`offline-root`) | **1** (`e7-lab-fictional-update`) | **0** | **1** |

The config XML advertises **one content source** (`offline-root`), not two independently configured software/firmware gateways. All counts are from actual local v0.14.2 constants, **not** E7 in-memory state. The stage-2 payload hash remains `fc767282b8b8d10f18483a3a4ef0cd8767b4f78f1b3ce226b8ed192185c4fb7e`; stage-3 remains `16231226e06abd15d9aee680eee5b7b3098a8bc64af334d6b634794a6500d7fd`.

**Historical Nokia source-path linkage:**

1. [`CNcdLoadNodeOperationImpl::FolderRefL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp) in content-source mode creates/updates links and saves the folder node, but does **not** supply folder metadata. [`FolderDataL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp) is the path that invokes `CNcdNodeManager::DataHandlerL` to attach `FolderData` metadata, if the folder reference already exists. [`CNcdNodeManager::DataHandlerL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdnodemanager.cpp) assigns the metadata to the node. No `FolderData` is present in our stage-2 or stage-3 XML.
2. [`CNcdNode::State`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdnodeimpl.cpp) explicitly returns `EStateNotInitialized` when either link **or metadata** is missing. [`CNcdNodeProxy::State`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/client/src/ncdnodeproxy.cpp) makes the same check client-side.
3. [`CIAUpdateController::LocalContainerLoadL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatecontrollerimpl.cpp) loops root children and **skips any `EStateNotInitialized` child without recursing into it**. Thus, **if this historical node-state behaviour holds on E7 Belle and there is no separately cached metadata for our invented folder IDs**, the root's `offline-root` folder is skipped even if its child's `ItemData` successfully arrived. This is a *direct structural explanation* for the empty directory; it does **not** by itself explain why the active checking spinner never ends.
4. [`CIAUpdateController::LoadComplete`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatecontrollerimpl.cpp) invokes `LocalLoadL()` **after** the load completion callback, then calls `RefreshComplete`. Therefore a blank list *after manually leaving an unfinished spinner* may also be a **stale or not-yet-refreshed list**, not affirmative evidence of any of the above on the real handset.
5. [`CNcdNodeContentInfo::InternalizeL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdnodecontentinfoimpl.cpp) initialises the application UID to null. It parses the content ID as a UID **only when MIME matches SISX**. Our inert `application/octet-stream` descriptor therefore leaves UID null, another *potential* application-eligibility obstacle. However, [`CIAUpdateNodeContainer::AddNodeL`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatenodecontainer.cpp) accepts SA package *type* in principle, so **it is not correct to conclude that the octet-stream MIME automatically guarantees filtering**. Further logic and the exact Belle runtime matter.

**Revised evidence ranking:** Missing synthetic root-folder metadata is a **high-confidence fixture defect and a testable explanation of blank-list behaviour** under the historical parser state model. An outstanding extra gateway/completion operation is possible but **not established** from the single-source/two-folder distinction. The spinner remains undiagnosed; none of our server's three HTTP-200 socket-write counters constitutes a device-side parse ACK or callback.

**Constrained next *design*, not implemented:** Prepare a v0.14.3 **host-only** minimal fixture comparison inserting one inert `FolderData` record for `offline-root` into the root response *after* its `FolderRef`, while otherwise keeping the synthetic item, no package/download URI, response gates and the original child response intact. Verify the Nokia parser callback order, `FolderRefL` + `FolderDataL` association, and old/modified XML differences in automated tests **before** any decision to arm a phone. Consider secondary folder metadata separately only if needed; do not simultaneously change the configured content-source topology, payload MIME or retry/window logic. Do not conflate acceptance of metadata with safe installability. As before, the protected writable updater cache is not backed up for a verified rollback, so live handset changes require a separate risk decision.
