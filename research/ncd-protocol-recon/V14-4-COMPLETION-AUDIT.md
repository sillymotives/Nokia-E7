# Nokia E7 NCD v0.14.4: offline completion-path source audit

**Date:** 2026-10-11. **Scope:** source trace and exact shipped v0.14.4 XML inspection only. **No E7 commands, no cache changes, no new responder or SIS file.** The linked Symbian sources are historical (pre-Belle) and do not constitute an E7 trace.

## Physical observations to account for

- The owner ran **one v0.14.4 physical E7 check** after the one-shot v0.14.3 experiment. All three permitted HTTP 200 socket writes completed with no handler errors or rejected post-root requests: config, synthetic two-folder root and SISX-identity child metadata. The handset **continued spinning**, then displayed a **blank directory when leaving the check normally**.
- The E7 actually issued a child browse for our **invented `offline-root`** with `includeMetaData=false` on the parent and `metadataDepth=1` / `metadataPerLevel=1` in its response filter. This is evidence that the client reached a synthetic-source child-loading path, though an earlier cached link could have contributed. Host socket writes do **not** prove XML parsing or client-side acceptance.
- A later 30-second packet summary reported **zero Wi-Fi TCP/UDP packets**, but the filter and interface were not validated with a same-session known-good packet. It cannot distinguish a quiet completed transaction from a stuck callback or traffic outside the observation window/interface.

## Source-backed expected callback chain

1. **Client request selection:** [`CNcdLoadNodeOperationImpl::CreateRequestLC` L1637-L1734](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L1637-L1734) requests `includeMetaData=false` for the *parent* in `EChildren` mode while `ELoadMetadata` asks for child `metadataDepth=1`. Therefore the observed browse's parent `includeMetaData=false` **does not mean the E7 declined child metadata**.
2. **HTTP-to-parser boundary:** [`HandleHttpEventL` L395-L429](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L395-L429) passes HTTP response-body chunks to `iParser->ParseL()` and calls `iParser->EndL()` **only after** an NCD transport `ECatalogsHttpOpCompleted` event. The host's `wfile.write()` counter **does not verify** either client event.
3. **Parser-recognised XML shape:** [`CNcdPreminetProtocolResponseParser` L94-L140](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/protocol/src/ncd_parser_pp_response.cpp#L94-L140) recognises direct `entity` and `embeddedData`; [`EntityRefParser` L164-L303](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/protocol/src/ncd_parser_pp_entityref.cpp#L164-L303) recognises nested `ItemRef`; [`EmbeddedDataParser` L75-L171](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/protocol/src/ncd_parser_pp_embeddeddata.cpp#L75-L171) forwards `ItemData` and `FolderData` to the NCD entity observer. This is a **static parse-shape match**, not a tested Belle parser result.
4. **Node construction:** [`ItemRefL` L1074-L1112](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L1074-L1112) creates or updates the child link in `EChildren` mode; [`ItemDataL` L1125-L1242](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L1125-L1242) calls `DataHandlerL` for matching child metadata and queues loaded node identifiers. **These exact runtime callbacks have not been observed.**
5. **Parse and node-op completion:** [`CNcdParserImpl::EndL` L173-L193](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/protocol/src/ncdparserimpl.cpp#L173-L193) can yield `ParseCompleteL` once the async buffer drains. [`CNcdLoadNodeOperationImpl::ParseCompleteL` L497-L533](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L497-L533) goes to `EComplete` when neither queries nor remote-folder suboperations remain. Our literal XML contains **no query, remote URI, pending icon block or binary download** that would itself require such follow-up.
6. **An often-missed client IPC continuation:** [`EComplete` L2239-L2300](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/server/src/ncdloadnodeoperationimpl.cpp#L2239-L2300) states that a non-suboperation **does not finish until the client proxy sends another message**. It first emits `ENCDOperationMessageCompletionNodesUpdated` for loaded nodes. The client proxy [handles that at L263-L297](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/client/src/ncdloadnodeoperationproxy.cpp#L263-L297), calling `SendContinueMessageL` to restart the operation; [`CNcdBaseOperationProxy::SendContinueMessageL` L392-L416](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/ncdengine/provider/client/src/ncdbaseoperationproxy.cpp#L392-L416) sends an **asynchronous IPC Continue** if no call is active. This is a specific **network-silent pending state** consistent with, but **not proven by**, our spinner.
7. **IAUpdate loader completion:** [`CIAUpdateLoader::OperationComplete` L323-L421](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdateloader.cpp#L323-L421) advances via `NextLoadLoopL` and only invokes `iObserver.LoadComplete` once `iOperations.Count()==0`. An ordinary error on a completed operation would still normally propagate to `LoadComplete`; a permanently pending operation would not.
8. **From callback to spinner:** [`CIAUpdateController::LoadComplete` L852-L873](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatecontrollerimpl.cpp#L852-L873) runs `LocalLoadL` and signals `RefreshComplete`. The UI [`StartRefreshL` L613-L649](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/ui/src/iaupdateuicontroller.cpp#L613-L649) sets the refresh indicator **true**, while [`RefreshComplete` L1230-L1255](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/ui/src/iaupdateuicontroller.cpp#L1230-L1255) explicitly calls `SetUpdatesRefreshing(EFalse)` on normal refresh completion. Whether Belle uses this exact path remains unverified.

## What the blank list actually proves

It proves **only** that the fictional item never became visible after the checking UI was left. It does **not** establish the result of `LocalLoadL`: in this implementation [`CIAUpdateController::LoadComplete`](https://github.com/SymbianSource/oss.FCL.sf.mw.appinstall/blob/760927eba63e3324cceee974b9ed582da90cb9a3/iaupdate/IAD/engine/controller/src/iaupdatecontrollerimpl.cpp#L852-L873) only rebuilds the visible node list **after** a load completion event, and the owner exited an **unfinished** spinner. Even valid, cached metadata could remain undisplayed; even an invalid item might be filtered. We cannot distinguish these without device-side completion evidence.

## Ranked hypotheses, explicitly unproven

1. **Pending NCD client/server operation, including `NodesUpdated` → `Continue` IPC:** directly supported as a legitimate waiting state by source and would generate **no extra Wi-Fi traffic**. The E7 has **not** been observed in this state.
2. **Missing transport-completed or asynchronous parser-finished signal:** host socket completion is insufficient to prove `ECatalogsHttpOpCompleted`, `iParser->EndL` or `ParseCompleteL` happened.
3. **Other outstanding node suboperation or missed UI completion callback:** `CIAUpdateLoader` deliberately waits until its operation array drains; the UI flag requires a completion callback. Neither array nor callback has been instrumented on the phone.
4. **Static XML ineligibility or actual Belle parser divergence:** possible for the blank list, but neither the corrected FolderData nor SISX identity had any effect on the spinner. Static parser shape is recognisable; handset semantics remain unknown.

**Not justified:** inventing another XML tweak, adding real SIS installation bytes or a URL, rearming v0.14.4, clearing private cache, factory reset, declaring a firmware failure or claiming the phone has accepted the XML.

## Recommended next diagnostic boundary (not executed)

Obtain a **read-only on-device observation** of NCD/IAUpdate operation status or error/completion events, ideally the presence/absence of `NodesUpdated` / asynchronous `Continue` and `LoadComplete`. The existing E7 bridge's actual permissions and logging capabilities must be verified before suggesting any command. If no such instrumentation is possible, the lowest-level alternative is a **positive-controlled passive transport capture beginning before the one permitted update check** to see request/response FINs; this would be a *new* phone cache-mutating trial and needs separate judgment. The prior zero-packet capture, taken after the response and without control, is not sufficient.
